## Maven Build Lifecycle: Order Matters

Today we went deeper into how Maven structures the build process. The key thing that clicked for me is that Maven's lifecycle phases are **ordered** — running a later phase automatically runs everything before it. So if you run `mvn package`, it's already compiled and tested by the time the JAR is created.

The four phases we focused on:

- `mvn compile` — compiles source code from `src/main/java` into `target/classes`. Fast way to check if the code even builds, no tests run.
- `mvn test` — compiles and runs the test suite. Doesn't produce a package.
- `mvn package` — does everything above, then bundles the output into a JAR or WAR in the `target/` folder.
- `mvn install` — runs the full lifecycle and copies the artifact into your local `.m2/repository`, making it available to other Maven projects on the same machine.

One thing that tripped me up initially: **`mvn build` is not a real command**. "Build" is a general term you'll see in IDEs, but Maven's standard lifecycle has no phase with that name. Depending on what you actually want, you'd use `compile`, `package`, or `install`.

## Java Source, Target, and the Release Option

When the compiler processes your code, two separate settings come into play:

- **Source version** — controls which Java language features are allowed in your code.
- **Target version** — controls which JVM version the generated bytecode is intended for.

Both can be configured in `pom.xml` under `<properties>`:

```xml
<maven.compiler.source>8</maven.compiler.source>
<maven.compiler.target>8</maven.compiler.target>
```

But there's a catch: setting `source` and `target` alone doesn't prevent you from accidentally calling a Java API that didn't exist in your target version. You could write code that compiles fine but crashes at runtime on an older JVM because it references a method that wasn't there yet.

The safer approach is using the `release` option, which validates language features, bytecode version, and public API availability all at once:

```xml
<maven.compiler.release>17</maven.compiler.release>
```

Set `release` to whatever's the oldest Java version your app is supposed to run on.

## Character Sets and Encoding

We also touched on encoding, which is something easy to ignore until it causes baffling bugs.

A **character set** defines the collection of characters that can be represented. A **character encoding** defines how those characters map to bytes on disk or in transit. The two terms often get used together in tools and config files.

Common encodings we went through:

- **UTF-8** — variable-length Unicode encoding, works for virtually every language, and stays compatible with ASCII for the first 128 characters.
- **UTF-16** — Unicode encoding using 16-bit code units, common in environments like Java's internal string representation.
- **ISO-8859-1** — single-byte encoding covering Western European characters, a common legacy format.
- **US-ASCII** — the original small encoding for basic English text, digits, and control characters.

UTF-8 is the standard choice for modern projects. In Maven, you can lock it in explicitly:

```xml
<project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
<project.reporting.outputEncoding>UTF-8</project.reporting.outputEncoding>
```

This keeps builds consistent regardless of what encoding the developer's operating system defaults to — which can differ between Windows, macOS, and Linux.

## Backward and Forward Compatibility

This distinction was useful to have clearly defined:

**Backward compatibility** means a newer version of something still supports things built for an older version. In Java, bytecode compiled for Java 8 will generally run on a Java 17 or Java 21 JVM without modification. The newer runtime knows how to handle the older class file format.

**Forward compatibility** is the opposite — an older system tolerating something built for a newer one. Java bytecode is **not** generally forward compatible. If you compile for Java 21, a Java 17 JVM will likely throw an `UnsupportedClassVersionError` because it doesn't understand the newer class file format.

The practical takeaway: if your application needs to run on a specific Java version, compile for that version. Don't compile for something newer and expect it to work unchanged.

## JUnit 5

JUnit is the standard testing framework for Java. It gives you the structure to write automated tests that verify your code does what it's supposed to do.

Key things JUnit 5 provides:

- `@Test` to mark a method as a test case
- `@BeforeEach` and `@AfterEach` for setup and teardown around each test
- Assertions like `assertEquals`, `assertTrue`, `assertThrows`
- Support for parameterized and nested tests
- Integration with Maven, Gradle, and IDEs

A basic example:

```java
import static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.api.Test;

class CalculatorTest {

    @Test
    void addsTwoNumbers() {
        Calculator calculator = new Calculator();

        int result = calculator.add(2, 3);

        assertEquals(5, result);
    }
}
```

Test classes go under `src/test/java` and are run with `mvn test`.

## Unit Testing vs Integration Testing

We wrapped up by covering the two main types of automated tests and why both matter.

**Unit testing** focuses on one small piece of behavior — typically a single method or class — in isolation. Dependencies like databases or external services get replaced with test doubles so the test only verifies the logic it's actually supposed to check. Unit tests are fast, straightforward to write, and pinpoint failures precisely.

**Integration testing** takes multiple components and verifies that they work together correctly. It might use a real database, a real file system, or an actual HTTP call. This kind of testing catches problems that unit tests can miss — things like mismatched interfaces, serialization issues, or incorrect data flow between modules. The tradeoff is that integration tests are slower and require more setup.

| Aspect | Unit Testing | Integration Testing |
|---|---|---|
| Scope | One small unit of behavior | Multiple connected components |
| Dependencies | Usually replaced with test doubles | Often uses real implementations |
| Speed | Fast | Slower |
| Purpose | Verify local logic | Verify component interactions |
| Failure diagnosis | Usually straightforward | May need investigation across components |

Both types are necessary — unit tests validate the pieces, integration tests confirm the pieces work together.

## Summary

A few things that stood out from today:

- Maven lifecycle phases are ordered — later phases include all the earlier ones.
- `mvn build` is not a real Maven command; pick the phase that matches what you actually need.
- The `release` compiler option is safer than `source` + `target` because it also validates the API surface.
- Always set source encoding explicitly in Maven to keep builds consistent across platforms.
- Older Java bytecode runs on newer JVMs, but not the other way around — compile for your minimum supported version.
- JUnit 5 makes it straightforward to write automated, repeatable tests in Java.
- Unit tests and integration tests serve different purposes and both belong in a healthy test suite.
